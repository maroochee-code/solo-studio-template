# 단계 규칙: 구현

## 목표
마일스톤 단위로 기능을 붙여 클로즈 베타 가능한 상태까지 만든다.

## 진행 순서
1. **골격 먼저 (총괄 단독)**: 코어 구조, Base 클래스, integrations 창구, 샘플 기능 1개씩
   → 사용자가 직접 실행해서 확인 → 승인 전에는 병렬 작업 금지
2. 마일스톤의 워크리스트를 작업 단위로 쪼개 실무 에이전트에 분배
   - (규모 M 이상) 기능 구현 전에 해당 기능 명세서와 UI 레이아웃이 사용자 승인된 상태인지 확인한다. 없으면 먼저 작성을 제안한다.
   - 구현하다 명세와 달라져야 하면 임의로 바꾸지 않고 보고한다. 승인된 변경은 명세서 수정 이력에 남긴다.
   - 각 작업: 담당, 할 일, 수정 가능 폴더, 완료 조건(통과해야 할 테스트)
3. 작업이 끝날 때마다 reviewer 검수
   - 기능 단위가 끝나면 구현 전달서(`docs/templates/feature-handoff.md`)를 `docs/handoff/<버전>/`에 작성한다.
     기획서와 다른 점, 데이터 세팅 방법, 치트·디버그 명령, 정상/버그 구분을 반드시 포함한다.
   - 테스트에 필요한 치트·디버그 기능은 기능과 함께 만들고, 라이브 빌드에서는 빠지게 한다.
   - 중요 시점에는 기술 리뷰 회의(`docs/templates/review-session.md`)를 제안한다.
4. 마일스톤 종료 시: QA 평가지, CHANGELOG, 회고(`docs/templates/retro.md`), 진행 체크리스트 점검

## 규칙
- 섹션 4의 경보 장치를 적극 가동한다.
- 담당 범위 밖 수정이 필요하면 실무자가 직접 고치지 않고 총괄에게 요청한다.
- 외부 SDK가 중간에 들어오면 바로 붙이지 않고 sdk-review 양식으로 먼저 검토한다.
- 성능 예산(있다면 architecture.md)을 마일스톤마다 측정해 보고한다.

## 응답 방식
작업 단위로 진행하고 끝날 때 3줄 요약.
