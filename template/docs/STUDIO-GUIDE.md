# 1인 개발 스튜디오 템플릿 (사람용 안내서)

Claude Code를 **개발 총괄**로 두고, 필요할 때 실무 에이전트를 "고용"하며,
프로젝트 규모(S/M/L)와 단계(프로토타입 → 본설계 → 구현 → 베타 → 라이브 → 동결)에 따라
대응 방식이 바뀌도록 만든 프로젝트 시작 세트입니다.

나는 **기획·사업·개발 총괄을 겸한 최종 결재자**, Claude는 **개발 총괄 + 실무 팀**입니다.

---

## 1. 새 프로젝트 시작하기
**권장: 세팅 스킬(studio-setup) 사용**
새 프로젝트 폴더에서 Claude에게 "스튜디오 세팅해줘" 또는 "studio-setup으로 새 프로젝트 시작"이라고 하면,
템플릿 복사 → 몇 가지 질문 → 상태 표·개요 작성 → 첫 결정 기록까지 해 줍니다.
기존 프로젝트에 적용, 규모 올리기, 템플릿 업데이트 반영도 같은 스킬로 합니다.

**수동으로 할 때**
1. 템플릿 저장소의 `template/` 폴더 안 내용을 새 프로젝트 폴더로 복사합니다. (`.claude`, `.gitignore`처럼 점으로 시작하는 파일도 포함)
2. `CLAUDE.md` 맨 위 **상태 표**를 채웁니다. 처음엔 보통 `규모 S, 단계 프로토타입`.
3. 프로젝트 폴더에서 Claude Code를 열고 이렇게 시작합니다.

```
CLAUDE.md와 현재 단계 규칙을 읽어줘.
만들고 싶은 건 [한두 문장]이야. 핵심 가치는 [이게 되면 성공].
프로토타입 범위와 가장 먼저 검증할 리스크를 제안해줘. 코드는 내가 승인하면 짜.
```

## 2. 폴더 안내
| 위치 | 무엇 |
|---|---|
| `CLAUDE.md` | Claude가 매 세션 읽는 규칙 카드. 상태 표, 총괄 역할, 결재 목록, 경보 장치 |
| `docs/rules/` | 규모 가이드, 단계별 규칙 6종 |
| `docs/agent-roster/` | **대기 인력풀** (아직 고용 안 된 에이전트 견본 12종) |
| `.claude/agents/` | **고용된 에이전트**. 처음엔 reviewer 하나 |
| `docs/checklists/` | 시작 / 진행 중 / 출시 / 라이브 운영 체크리스트 ([S][M][L] 표시) |
| `docs/templates/` | 설계 변경·충원·단계 전환·SDK 검토·플랫폼 공지·회의록·기획서·QA·회고·포스트모템 양식 |
| `docs/` 나머지 | 범위, 리스크, 결정 기록, 기술 부채, 마일스톤, 아키텍처, 수집 데이터, 출시 runbook |

## 3. 프로젝트가 돌아가는 방식
- **총괄이 감시하고 제안합니다.** 오류 반복, 코드 반복, 규모 증가, 범위 밖 요구, 외부 SDK 요청, 플랫폼 공지 등이 감지되면 양식에 맞춰 제안합니다. (`CLAUDE.md` 4장)
- **결정은 내가 합니다.** 설계 변경, 단계·규모 변경, 에이전트 고용, 라이브 배포, 결제, 스토어 제출은 승인 없이는 진행하지 않습니다. (`CLAUDE.md` 3.1)
- **미룬 제안은 기록됩니다.** "지금은 아니다" → `tech-debt.md`. 같은 문제가 세 번째 생기면 다시 제안합니다.
- **문서가 기억입니다.** Claude Code는 세션이 바뀌면 대화를 기억하지 못합니다. 결정·회의록·기획서가 다음 세션의 맥락이 됩니다.

## 4. 자주 쓰는 지시
| 상황 | 이렇게 말하기 |
|---|---|
| 아이디어만 던질 때 | "기획자로서 제안하는 거야. 총괄 입장에서 검토해서 문제 있으면 반대해줘." |
| 프로토타입 끝 | "단계 전환 검토해줘." |
| 규모가 커진 것 같을 때 | "앞으로 [기능들]을 붙일 건데, 지금 구조로 버틸 수 있는지 진단만 해줘." |
| 인력이 필요해 보일 때 | "지금 에이전트 구성 점검하고 필요하면 충원·정리 제안해줘." |
| SDK가 들어왔을 때 | "이 SDK 문서 보고 연동 검토해줘. 아직 붙이지는 마." |
| 플랫폼 메일이 왔을 때 | "이 메일 영향 분석해줘. 진짜 메일인지도 확인하고." |
| 회의(결정) 끝 | "방금 결정한 거 회의록이랑 결정 기록 남기고 관련 문서 갱신해줘." |
| 마일스톤 끝 | "진행 중 체크리스트 점검하고 QA 평가지, 회고 만들어줘." |
| 기능 테스트 전 | "이 기능 구현 전달서 보여줘. 세팅이랑 테스트 방법, 기획서랑 다른 점 위주로." |
| 직접 설명이 필요할 때 | "이 기능 어떻게 돌아가는지 코드 모르는 기획자한테 설명하듯 알려줘." |
| 중요한 단위가 끝났을 때 | "이 부분 기술 리뷰 회의 열어줘. 관점별로 따로 보고 종합해서 브리핑해줘." |
| 출시 직전 | "동결 단계로 전환하고 출시 체크리스트 최신 정책 기준으로 점검해줘." |
| 라이브 버그 | "라이브 핫픽스 규칙으로 처리해줘. 원인부터." |

## 5. 에이전트 고용
1. 총괄이 `hiring-proposal` 양식으로 제안 (또는 내가 요청)
2. 승인하면 총괄이 `docs/agent-roster/`의 견본을 `.claude/agents/`로 복사하고 프로젝트에 맞게 수정
3. **새 세션부터** 사용 가능

처음부터 많이 고용하지 마세요. 에이전트는 부를 때마다 맥락을 새로 읽어서 사용량이 늘어납니다.
"늦어진 프로젝트에 인력을 더 넣으면 더 늦어진다"는 말은 에이전트에도 적용됩니다.

## 6. 규모별로 가볍게 쓰기
- **S (개인 툴, 봇)**: 상태 표 + scope.md 3줄 + decisions.md 정도면 충분. 에이전트 없이 시작해도 됩니다.
- **M (외부 사용자, 서버·스토어)**: 본설계부터 문서와 reviewer, 실무 1~3명.
- **L (결제, 퍼블리셔, 라이브)**: 전체 사용. 출시·운영 체크리스트는 시작 단계부터 보세요.

## 7. 주의
- 정책·규격·요금 정보는 자주 바뀝니다. 체크리스트의 항목은 "확인할 것"이지 "정답"이 아닙니다. 출시 때마다 공식 문서 기준으로 확인하세요.
- 결제, 법규, 심의처럼 돈과 법이 걸린 판단은 퍼블리셔나 전문가 확인을 거치세요.
- 퍼블리셔·보안 업체 SDK 문서는 NDA가 걸린 경우가 많습니다. AI 도구에 넣어도 되는지 계약을 먼저 확인하세요.
- 회의록·결정 기록은 Claude가 정리한 뒤 내가 한 번 읽고 확정합니다.
- 프로젝트가 끝나면 포스트모템을 쓰고, 배운 규칙을 이 템플릿에 다시 반영하세요. 그렇게 나만의 "코어"가 쌓입니다.
