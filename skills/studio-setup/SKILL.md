# studio-setup — 1인 개발 스튜디오 세팅

사용자는 기획·사업·개발 총괄을 겸하는 최종 결재자이고, Claude는 프로젝트의 개발 총괄을 맡는다.
이 스킬은 **세팅만** 담당한다. 프로젝트 규칙 자체는 세팅 후 프로젝트 안의 `CLAUDE.md`와 `docs/`에 있다.

## 템플릿 원본 위치
1. 로컬 우선: `D:\Github\solo-studio-template\solo-studio-template\template`
   - 있으면 그 저장소에서 `git pull`로 최신화를 시도한 뒤 사용한다. (실패해도 로컬 파일로 진행하고 알린다)
2. 로컬에 없으면 GitHub: `https://github.com/maroochee-code/solo-studio-template` (비공개 저장소)의 `template/` 폴더
   - 임시 폴더에 `git clone --depth 1` 후 `template/`만 사용한다.
3. 둘 다 안 되면 멈추고 사용자에게 템플릿 위치를 묻는다. 기억으로 템플릿을 지어내지 않는다.

템플릿 버전은 `template/.studio-template-version`에 있다.

## 먼저 할 일: 모드 판단
사용자의 말과 현재 폴더 상태로 모드를 고른다. 애매하면 묻는다.
| 상황 | 모드 |
|---|---|
| 빈 폴더이거나 막 시작하는 프로젝트 | A. 새 프로젝트 |
| 코드가 이미 있는데 `.studio-template-version`이 없음 | B. 기존 프로젝트에 적용 |
| 템플릿이 적용돼 있고 규모를 키우려 함 | C. 규모 올리기 |
| 템플릿이 적용돼 있고 템플릿이 더 새 버전임 | D. 템플릿 업데이트 반영 |

## A. 새 프로젝트
1. **대상 폴더 확인**: 현재 폴더가 맞는지 확인한다. 이미 파일이 있으면 B 모드를 제안한다.
2. **질문 (한 번에, 짧게)**
   - 무엇을 만드나요? (한두 문장)
   - 핵심 가치: 이게 되면 성공이라고 할 한 가지는?
   - 누가 쓰나요? (나만 / 지인 / 일반 사용자)
   - 플랫폼은? (윈도우, 웹, 안드로이드, iOS 등)
   - 결제, 퍼블리셔, 서버, 외부 SDK 예정이 있나요?
   - 이번에 **안 할 것**이 떠오르면 알려 주세요.
3. **규모 제안**: `docs/rules/scale-guide.md` 기준으로 S/M/L 중 하나를 근거와 함께 제안하고 승인받는다. 확신이 없으면 낮은 쪽으로 시작하고 상향 신호를 알려 준다.
4. **템플릿 복사**: `template/` 안의 모든 파일(점으로 시작하는 `.claude/`, `.gitignore`, `.env.example`, `.studio-template-version` 포함)을 대상 폴더에 복사한다. 이미 같은 이름의 파일이 있으면 덮어쓰지 말고 보고한다.
5. **채우기**
   - `CLAUDE.md` 제목의 `[프로젝트명]`, 0장 상태 표(규모, 단계=프로토타입, 플랫폼), 2장 개요의 "무엇을", "핵심 가치"
   - `docs/scope.md`: 이번 버전에 할 것 / 안 할 것
   - `docs/risks.md`: 가장 불확실한 것 1~3개 (사용자 답에서 추론한 것은 "제안"이라고 표시하고 확인받는다)
   - `docs/decisions.md`: 오늘 날짜로 "프로젝트 시작: 규모 _, 프로토타입 단계" 기록
6. **git**: 저장소가 아니면 `git init`을 제안하고, 승인되면 첫 커밋 "프로젝트 시작: 스튜디오 템플릿 v<버전> 적용"을 만든다.
7. **규모 S라면** 가볍게 쓰는 법을 3줄로 안내한다 (상태 표, scope.md, decisions.md만 신경 쓰면 됨).
8. **마무리 안내**: 이제부터 `CLAUDE.md`와 `docs/rules/stage-1-prototype.md` 규칙으로 진행한다고 알리고, 프로토타입 범위와 첫 검증 리스크를 제안한다. 코드는 승인 후에 짠다.

## B. 기존 프로젝트에 적용
1. 프로젝트를 훑어 **현재 단계와 규모를 추정**한다: 코드 규모, 테스트 유무, 배포·스토어·서버·결제·외부 SDK 흔적, 사용자 존재 여부. 근거와 함께 제안하고 승인받는다.
2. **덮어쓰기 금지**. 특히 기존 `CLAUDE.md`, `README.md`, `.gitignore`가 있으면:
   - `CLAUDE.md`: 기존 내용을 템플릿 `CLAUDE.md`의 2장(개요)·8장(명령어)·적절한 곳으로 옮겨 합친 안을 만들어 **차이를 보여 주고** 승인 후 반영
   - `.gitignore`: 템플릿 항목 중 없는 것만 추가 제안
   - `README.md`: 건드리지 않는다 (템플릿 안내서는 `docs/STUDIO-GUIDE.md`)
3. 나머지 템플릿 파일 중 없는 것만 복사한다.
4. 현재 구조를 바탕으로 `docs/architecture.md` 초안을 채우고, 규칙과 어긋나는 현재 코드(외부 SDK 직접 호출, 비밀값 노출, 문구 하드코딩 등)를 목록으로 보고한다. **바로 고치지 않는다.** 고칠 것은 tech-debt.md 또는 change-proposal로.
5. `docs/decisions.md`에 "스튜디오 템플릿 v<버전> 적용, 규모 _, 단계 _" 기록 후 커밋 제안.

## C. 규모 올리기
1. 현재 상태 표와 `scale-guide.md`의 상향 신호를 대조해 상향 근거를 정리한다.
2. 새 규모에서 **새로 켜지는 항목** 목록을 만든다 (scale-guide의 "규모별로 켜는 것" 표 기준). 체크리스트에서 새 규모 표시 항목도 뽑는다.
3. 필요한 에이전트 충원안을 hiring-proposal 양식으로 만든다 (최소 인원).
4. 승인되면 상태 표 갱신, decisions.md 기록, 필요한 문서 초안 생성, 승인된 에이전트를 `docs/agent-roster/`에서 `.claude/agents/`로 복사해 프로젝트에 맞게 수정한다. 새 에이전트는 다음 세션부터 쓸 수 있다고 알린다.
5. 하향(규모 축소)도 같은 방식으로 처리한다: 꺼지는 절차와 정리할 에이전트를 제안.

## D. 템플릿 업데이트 반영
1. 프로젝트의 `.studio-template-version`과 최신 템플릿 버전을 비교한다. 같으면 알리고 끝낸다.
2. 템플릿 저장소의 git 기록에서 두 버전 사이 변경 내용을 요약한다.
3. **반영 대상은 규칙·양식만**: `docs/rules/`, `docs/templates/`, `docs/checklists/`, `docs/agent-roster/`, `docs/STUDIO-GUIDE.md`, `CLAUDE.md`의 규칙 장(1, 3~7장).
4. **절대 덮어쓰지 않는 것**: 프로젝트가 채운 문서 (`CLAUDE.md` 0·2·8장, decisions, scope, risks, milestones, architecture, tech-debt, 회의록, 기획서, QA, compliance, release runbook), 그리고 프로젝트에 맞게 수정된 `.claude/agents/`.
5. 파일별로 차이를 보여 주고 승인받은 것만 반영한다. 프로젝트에서 의도적으로 바꾼 규칙과 충돌하면 양쪽을 보여 주고 사용자가 고르게 한다.
6. `.studio-template-version` 갱신, decisions.md 기록, 커밋 제안.

## 템플릿 자체를 개선할 때
프로젝트 회고·포스트모템에서 "다음 프로젝트에도 쓸 규칙"이 나오면, 템플릿 저장소에 반영하자고 제안한다.
반영할 때는 템플릿 저장소의 `template/`을 수정하고, `.studio-template-version`의 버전을 올리고(규칙 추가는 중간 자리, 오타 수정은 끝자리), 커밋 메시지에 무엇이 왜 바뀌었는지 적는다. 푸시는 사용자가 GitHub Desktop 등으로 직접 한다.

## 항상
- 사용자 승인 없이 기존 파일을 덮어쓰거나 지우지 않는다.
- 사용자가 말하지 않은 내용을 결정 사항으로 기록하지 않는다. 추론한 것은 "제안"으로 표시한다.
- 세팅이 끝나면 무엇을 만들었고 무엇을 채워야 하는지 5줄 이내로 보고한다.
